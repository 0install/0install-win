# Improve translations

## How translations work in this repo

There are two kinds of localized resources:
- **String resources:** `src/<Project>/Properties/Resources.resx` in `Central.WinForms` and `Store.Service`, used from code as `Resources.<Key>`. Resource name: the project name (e.g. `Central.WinForms`).
- **WinForms forms:** `src/<Project>/<Form>.resx` for `IntroDialog`, `MainForm`, `PortableCreatorDialog`, `SelectCommandDialog`, `SyncWizard` (`Central.WinForms`) and `ConfigDialog`, `FeedSearchDialog`, `IntegrateAppForm`, `InterfaceDialog`, `StoreManageForm` (`Commands.WinForms`). Keys are `<control>.<Property>` (`buttonHelp.Text`, `columnName.HeaderText`, `checkBoxAutoUpdate.ToolTip`, `$this.Text` for the window title). Resource name: `<Project>/<Form>` (e.g. `Central.WinForms/MainForm`). The source file also contains layout properties and `>>` metadata; only keys present in the localized files are translatable (the translate workflow strips the rest before uploading/translating), and the scripts only show those.

For both kinds:
- The English source (`Resources.resx`, `<Form>.resx`) must never be edited as part of this skill.
- `<Base>.<lang>.resx` is the committed, combined translation the build uses. Note that `<Form>.cs.resx` is the **Czech** translation, not a code-behind file. It is generated by the monthly `.github/workflows/translate.yml` run (`MrMeeseeks.ResXTranslationCombinator`) from:
  - `<Base>.<lang>.o.resx`: human translations pulled from Transifex (gitignored). Become entries with `<comment>Manually overriden.</comment>`.
  - `<Base>.<lang>.a.resx`: DeepL output (gitignored, cached in CI). Used for keys without a human translation; become entries with `<comment>Automatically translated.</comment>`.
- DeepL (with the `Zero Install` glossary) fills gaps for `cs el es fr id it ja ko nl pl pt-PT ro ru zh`. `de`, `pt-BR` and `tr` are human-only.
- Because the combined files are regenerated every month, **an improvement only survives if it is also uploaded to Transifex**. That is why step 6 exists.
- `.tx/config` maps each file to a Transifex resource in the `0install-win` project (e.g. `central`, `window-central_winforms_mainform`) and `pt-PT`/`pt-BR` to `pt_PT`/`pt_BR`.

Most of the GUI's text is not in this repo: messages, CLI help and many dialog texts come from the `ZeroInstall.*` NuGet packages (0install-dotnet) and generic labels from `NanoByte.Common`. Those have their own copy of this skill in their repositories. If the user asks about a string that is not found here, check those repositories (see the local NuGet source index if available) and point the user there.

Helper scripts live in `.claude/skills/improve-translations/scripts/` (PowerShell 5.1 and 7 compatible). Run them from the repository root.

When writing your own ad-hoc PowerShell for this skill, keep in mind:
- Windows PowerShell 5.1 reads `.ps1` files without a BOM as ANSI, which garbles non-ASCII literals (umlauts, CJK). Keep scripts ASCII-only and build non-ASCII characters from char codes (e.g. `[char]0x00AB`), save them with a UTF-8 BOM, or run them with `pwsh`. Don't rely on `\uXXXX` escapes written through file-editing tools, because they may be turned into literal characters.
- Typographic quotes (`“ ” „ ‘ ’`) are string delimiters in PowerShell, so don't put them in inline commands; use char codes instead.
- In Windows PowerShell 5.1, `ConvertFrom-Json` emits a JSON array as a single object. Unroll it with `| ForEach-Object { $_ }` before grouping or counting.
- `-eq`/`-ne`/`-contains` ignore case. Use `-ceq`/`-cne` when comparing translations, or case-only fixes look like no-ops.
- Read JSON and `.resx` files with an explicit UTF-8 encoding (`Get-Content -Encoding UTF8` or `[IO.File]::ReadAllText`).
- Call the scripts in-process (`.\.claude\...\Script.ps1 -Languages fr,ja`), not via `powershell -File`, which passes `fr,ja` as a single string.
- Form keys like `$this.Text` must be single-quoted in PowerShell.

## Workflow

### 1. Determine scope

Parse the arguments into languages (file-name codes such as `fr`, `pt-BR`) and resources. `-Projects` accepts resource names (`Central.WinForms/MainForm`, `Store.Service`) and project names (`Central.WinForms` selects its `Resources.resx` and all its forms).
- Languages default to **all** localized languages, including `de`, `pt-BR` and `tr`.
- Resources default to all; process them one project at a time so batches stay reviewable.
- Make sure the working tree has no uncommitted changes to `*.resx` files, so that `HEAD` is a clean baseline for detecting what this run changed. If there are, ask the user how to proceed.

### 2. Gather context

For each project, dump the strings with the code that uses them into the scratchpad:

```powershell
.claude/skills/improve-translations/scripts/Get-TranslationContext.ps1 -Projects Central.WinForms -Languages fr,ja -OutFile <scratchpad>/Central.WinForms.txt
```

Options: `-Status Auto|Manual|Missing` to narrow down, `-Keys` for specific keys, `-MaxUsages` for more call sites. Read the output in chunks. Each block shows the English source, up to three usages with surrounding code, and every translation with its status (`auto`, `manual`, `missing`). For form keys, the first usage is the control's declaration in `<Form>.Designer.cs`, which tells you its type (`Button`, `ToolStripMenuItem`, `Label`, `CheckBox`, `DataGridViewColumn`, ...), followed by references in `<Form>.cs`. Open `<Form>.Designer.cs` to see the control's parent (menu, group box, tab page) and its neighbours when that matters for the wording or available space.

Also run the mechanical checks and include their findings in the review:

```powershell
.claude/skills/improve-translations/scripts/Test-Translations.ps1 -Projects Central.WinForms -Languages fr,ja -CountStraySpaces
```

Besides errors for placeholder mismatches (including format specifiers such as `{0:0.00}`), it warns about mismatched quote marks around placeholders. `-CountStraySpaces` adds the number of entries per file with the stray-space artifact described in step 3.

**Glossary from 0install-dotnet:** this GUI shows Zero Install terms side by side with strings from 0install-dotnet, so terminology must match there. If a 0install-dotnet checkout is available (e.g. next to this repository, or via the local NuGet source index for `ZeroInstall.Commands`), dump its human translations as the primary glossary source:

```powershell
<0install-dotnet>/.claude/skills/improve-translations/scripts/Get-TranslationContext.ps1 -Languages fr -Status Manual -MaxUsages 0 -OutFile <scratchpad>/glossary-fr.txt
```

If it is not available, build the glossary from this repository's `manual` entries only and say so in the review.

**Wizard buttons:** the Next, Back, Cancel and Finish buttons of `SyncWizard` come from the AeroWizard library's own satellite assemblies, not from this repository. Strings that refer to them (e.g. `labelRegister2`, "click on 'Next'") must match what the user actually sees. This script prints the button texts per language, or says that the language falls back to English (no AeroWizard translation, or excluded by `SatelliteResourceLanguages` in `src/Directory.Build.props`):

```powershell
.claude/skills/improve-translations/scripts/Get-WizardButtonTexts.ps1 -Languages fr,ja
```

When reviewing many languages, delegate one language per subagent. Run them with `model: "sonnet"`; Sonnet handles this review well, and 16 parallel Opus subagents exhausted the session limit in an earlier run. Each subagent must **only report proposals, not edit files**:
- Generate one context file per language across all resources (`-Languages fr -OutFile <scratchpad>/lang/fr.txt`) instead of per project.
- Point every subagent at the brief [subagent-brief.md](subagent-brief.md) instead of repeating the review criteria in each prompt. Its prompt must give:
  - the language;
  - the paths of the context, glossary and output JSON files (`<scratchpad>/proposals/<lang>.json`);
  - the user's scope decisions for stray spaces and missing access keys (see step 3);
  - for languages with translated wizard buttons, the output of `Get-WizardButtonTexts.ps1`;
  - any language-specific hints (e.g. human-only language, pt-PT vs. pt-BR mix-ups, mechanical check warnings).
- The brief tells the subagent to write the proposals JSON in the format `Apply-Translations.ps1` expects (see step 5) and to check it with `-WhatIf`. It replies with:
  - the number of proposals per resource;
  - its terminology;
  - systematic issues it left unfixed;
  - errors in the 0install-dotnet glossary itself.

  Pass the unfixed issues on to the user, and report glossary errors as issues for 0install-dotnet.
- If a subagent fails (e.g. a rate limit), delete any partial proposals file it left before starting a new one. Alternatively, resume the stopped subagent with `SendMessage`.
- Review the subagents' changes to `manual` entries before applying them, e.g. by listing their reasons, since they override human decisions. If a subagent changed the register (formal vs. informal address), check it against the glossary, e.g. by counting formal and informal forms in its manual entries.

### 3. Find poor translations

Review `auto` entries first; they are the most likely to be wrong. Review `manual` entries too, but only propose changes for clear errors, since they are human decisions.

Work out how each string is used: button, menu item, tab, label, check box, column header, tool tip, window title, accessible name (screen readers, should describe the control), hint text in an empty text box, message box text, tray notification, progress/task name, exception message, log message, CLI output (`Store.Service`). Then check for:

- **Meaning in context:** literal translations that pick the wrong sense of an ambiguous word (e.g. "store" as noun vs. verb, "run"/"feed"/"interface"/"implementation"/"catalog"/"app list"/"sync" as Zero Install terms vs. everyday words, "integrate", "capabilities").
- **Terminology consistency:** align with the 0install-dotnet glossary (see step 2) and this repository's `manual` entries for recurring Zero Install concepts. When you change a term, check the language's other strings and forms for the same term. Labels that refer to other UI elements (e.g. "click Integrate", "the Options dialog") must match the translation of that element. That includes the wizard buttons from AeroWizard (see step 2).
- **Things that must stay literal:** command names (`0install run`, `0install central`, ...), option names (`--batch`), XML element/attribute names and values (`<implementation>`, `stability`, `testing`), file names, environment variables, URLs, product names (Zero Install, 0install, Zero Install for Windows).
- **Access keys:** an `&` in button, menu, tab and label texts marks the keyboard access key (`&Help`); `&&` is a literal ampersand. Keep exactly one `&` if the source has one. Put it on a letter that occurs in the translated word, preferably the first letter, and avoid letters already used by sibling controls of the same menu or dialog (check the neighbours in `<Form>.Designer.cs`). For Japanese, Korean and Chinese, the convention is to append `(&H)` with the Latin letter of the English access key, e.g. `ヘルプ(&H)`. DeepL drops access keys entirely, so most `auto` entries lack them.
- **Fitting the layout:** WinForms controls are sized for the English text. Keep labels, buttons, tabs and column headers about as short as the source; prefer the shorter of two equivalent phrasings and the usual terse UI style (no articles or "please" on buttons). The check script warns about translations much longer than the source.
- **Placeholders and formatting:** every `{0}`, `{1}`, ... preserved; line breaks and leading/trailing whitespace preserved; quotes around placeholders following the language's conventions (watch out for DeepL artifacts like `«{0} »` with a stray space).
- **Grammar with placeholders:** the sentence must still be grammatical once `{0}` is substituted (e.g. gender/case agreement, word order for a file path vs. a name; counts vs. names).
- **Register and tone:** consistent formal/informal address within a language matching the manual entries and 0install-dotnet; imperative vs. infinitive for buttons and menu items as is conventional for the language (follow the platform's conventions, e.g. German uses infinitives); no overly literal or verbose phrasing for short labels.
- **Untranslated or mixed-language text** that should be translated, and translations that are simply wrong or incomplete.

Errors that came up repeatedly in past runs of this skill in 0install-dotnet, across many languages, and are likely here too:
- **Count placeholders read as names:** in strings like "Do you want to delete the {0} checked element(s)", DeepL often treats `{0}` as a label rather than a number.
- **Literal values translated:** `0install central` (became "centrale"), `%ProgramFiles%`.
- **Wrong word sense:** "store" became "shop"; "implementation" became "application" or "instance"; "desktop integration" became "desktop shortcut"; "feed" became a news feed; "catalog" became a print catalog.
- **Inverted meaning or direction:** "case insensitive" translated as "case sensitive"; "{0} of {1}" became "{1} of {0}".
- **Product name translated:** "Zero Install" became 零安装, 제로 인스톨 or ゼロインストール.
- **First-person or instruction-style phrasing:** status messages written as "I resolved…" or "Please open…" instead of descriptive text.
- **Stale manual entries:** some human translations were made from older English source texts and no longer match; compare meaning, not just wording.
- **Formatting artifacts:** DeepL artifacts such as backticks around placeholders, `l'{0} e`, and missing spaces (`{0}angefordert`); a lowercase sentence start or a capital mid-sentence after a placeholder.
- **Garbage:** placeholder text like `XXX` left in manual entries.

Seen in this repository:
- **Wrong word sense:**
  - "Setup integration" became "installer integration"; "Forgot key" became "forgot password";
  - "Extensions" (file types) became add-ons/plugins; "Source" (column) became "source code";
  - "checked entries" became "verified entries"; "Deploy" was translated with the word for "implementation";
  - "Sync account" became "synchronize the account"; "Match (%)" became a sports match.
- **Nouns and verbs swapped:** verbs on tabs and column headers, nouns on buttons.

Two artifacts affect many `auto` entries: the stray space (`«{0} »`, `„{0} “`, `「{0} 」`, `{0} を`) and dropped access keys. The `-CountStraySpaces` output shows how many entries have the stray space (it covers the quote cases, not spaces before particles like `を`). Fixing them turns each entry into a manual override that gets uploaded, so ask the user up front, separately for each of the two artifacts, whether to fix it everywhere or only in entries changed for other reasons. Pass the answers on to subagents.

### 4. Propose and confirm

Present the proposals per resource and language as a table: key, current text, proposed text, short reason (and whether the entry was `auto` or `manual`). Ask the user to approve, adjust or drop rows. Do not edit files before approval.

For large runs, ask the user up front which languages they want to review row by row; they may trust your judgment for languages they don't speak. Group repetitive rows (e.g. "restore access key" or "column headers: shorter wording") into one table row listing the keys, so the table stays readable.

### 5. Apply

For each approved row, edit `<Base>.<lang>.resx` with the Edit tool (do not reserialize the file with an XML library, so the combinator's formatting, UTF-8 BOM and LF line endings stay intact):
- Replace the `<value>` text, XML-escaping `&` (so an access key is written `&amp;`), `<` and `>`.
- Set the entry's comment to exactly `<comment>Manually overriden.</comment>` (keep this spelling; it is what the combinator emits) if it is not already.
- Do not touch any other entry, and never add layout properties (sizes, locations) to localized form files.

For many proposals (e.g. from subagents), put them in a JSON file per language instead and apply them with the script. It does the same exact in-place replacement. It skips a proposal with a warning when:
- its `old` doesn't match the current value exactly (case-sensitive, including trailing line breaks);
- its `new` fails validation against the English source: it must keep the same placeholders, access key count, number of line breaks and leading/trailing whitespace, and must differ from `old` (case-sensitively).

```powershell
.claude/skills/improve-translations/scripts/Apply-Translations.ps1 -Path <scratchpad>/proposals/fr.json -Language fr [-SkipKeys 'Central.WinForms/MainForm/buttonHelp.Text'] [-SkipValidation '<Project>/<Key>'] [-WhatIf]
```

Run it with `-WhatIf` first and fix every proposal it warns about. Subagents occasionally drop a trailing line break from `old` or an access key from `new`. Use `-SkipValidation` only for intended differences, such as restoring a line break the translation was missing. Afterwards, `git diff --numstat` should show equal insertions and deletions per file, except where a line-break fix was intended.

Then validate the changed entries and the build:

```powershell
.claude/skills/improve-translations/scripts/Test-Translations.ps1 -Base HEAD
dotnet build src
```

Fix any errors before continuing. Review warnings and fix them unless they are intentional. For layout warnings on important dialogs, offer the user to check the form visually (e.g. run `0install-win` with the UI culture set to that language).

### 6. Upload changed entries to Transifex

Generate `.o.resx` files containing **only the manually overriden entries changed in this run** (compared against `HEAD`; use `-Base <commit>` if the changes are already committed):

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1
```

The script writes the files at the paths `.tx/config` expects, overwriting any stale local copies from earlier `tx pull`s. It prints:
- each file with its keys;
- the total number of entries per language;
- one push command per Transifex resource (one per form), listing only the affected languages, so no other local `.o.resx` file is uploaded.

Partial files only update the keys they contain; other translations on Transifex are left alone. Check that the totals match the number of applied proposals.

Show the user the number of entries per language, the resources and the push commands. **Ask for confirmation before pushing**, since this publishes the translations. The Transifex CLI reads the API token from `~/.transifexrc` or the `TX_TOKEN` environment variable; never ask for, print or store the token. If authentication fails, tell the user to set it up themselves.

After confirmation, rerun the script with `-Push`. It writes the same files, runs the printed commands from the repository root and prints only the non-progress output of the CLI:

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1 -Push
```

The resource argument must be in the CLI's `<project>.<resource>` form (e.g. `0install-win.window-central_winforms_mainform`), which the script uses. The full `.tx/config` section name (`o:eicher:p:0install-win:r:window-central_winforms_mainform`) makes the CLI exit with code 1 and print nothing. If a push fails silently, `tx status` (same CLI, no network needed) shows which resources the CLI sees.

The CLI skips files whose remote translation is newer, e.g. because someone edited it on Transifex. Its status lines are cut to the console width (`[fr] - Skipping becau..`), so skips are easy to miss when running the commands by hand. `-Push` collects them and lists each skipped file with its keys, plus a `--force` command for just those resources and languages. Report the skipped keys to the user instead of forcing right away. If the user decides to force them, run the printed `--force` commands while the generated files still exist. If the files are already removed, regenerate them first (with `-Base HEAD~1` if the changes are already committed), e.g. `-Push -Force -Projects <resource> -Languages <lang>`.

Some languages may have old `.o.resx` files left over from earlier `tx pull`s. They are harmless as long as only the printed per-resource commands are used, because those commands list only the languages written in this run.

Afterwards remove the generated files so they cannot be pushed again by accident (use the same `-Base` as before):

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1 -Remove
```

### 7. Commit

Commit only the changed `<Base>.<lang>.resx` files, e.g. `Improved fr and ja translations`. Do not push unless the user asks.
